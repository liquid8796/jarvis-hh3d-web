CanvasBlocker — Chrome port
===========================

A port of [CanvasBlocker](https://github.com/kkapsner/CanvasBlocker) 1.12 (a
Firefox add-on) to Chrome / Chromium, manifest V3. `README.md` is the original
project's documentation; this file describes what the port changes and why.

Requires **Chrome 119 or newer** (manifest `world: "MAIN"` content scripts and
`match_origin_as_fallback`).


Installing
----------

1. Open `chrome://extensions`.
2. Turn on **Developer mode**.
3. **Load unpacked** → select this folder.

The options page opens on first install, same as on Firefox.


Building
--------

The repository is directly loadable — the generated files are committed. Rerun
the generators after changing the corresponding sources:

| Command                  | Regenerates                                    | Rerun when                       |
| ------------------------ | ---------------------------------------------- | -------------------------------- |
| `node build/bundle.js`   | `content/injected.js`, `content/messageKeys.js` | any `lib/*.js` used in the page  |
| `node build/locales.js`  | `_locales/*/messages.json` (key names)          | translations were added/changed  |
| `node build/icons.js`    | `icons/png/*.png`                               | an SVG icon changed              |
| `node build/verify.js`   | nothing — runs the end-to-end checks            | before shipping a change         |

`build/verify.js` launches Chrome twice (with and without the extension) against
`build/verify-page.html` and compares what the page can observe, then checks the
service worker, the network rules, the notification chain and every extension
page. It exits non-zero on failure.


What had to change
------------------

### Injection: Xray vision → MAIN world + a bridge

The Firefox version ran in the content-script sandbox and reached into the page
through `wrappedJSObject` / `exportFunction`. Chrome has no equivalent, so the
protection now runs in the page's own world:

* `content/injected.js` — **MAIN world**, `document_start`. Generated by
  `build/bundle.js`, which concatenates the `lib/` modules into a *single*
  closure. That matters: MAIN-world content scripts share the page's global
  scope, so listing the files individually would publish `require`, `scope` and
  every module to the page.
* `content/bridge.js` — **ISOLATED world**, owns `chrome.*` and relays settings,
  translations, runtime messages and the port. The two halves talk over
  `CustomEvent`s under a per-document random name, exchanged through an
  attribute on `<html>` that is removed before any page script runs.

`lib/extension.js` is the adapter: `getWrapped` became the identity function,
and because a replacement function would otherwise stringify to its own source,
`Function.prototype.toString` is patched to report `[native code]` for
everything the extension installs.

Three places relied on Xray semantics — that a property read through the wrapper
returns the *native* value — and recursed infinitely when run inside the page.
They now call the captured original getter explicitly:
`lib/modifiedDOMRectAPI.js` (the faking getters and the internal reads that
build a fake rect) and `lib/iframeProtection.js`.

### Settings can no longer be awaited synchronously

Firefox stalled the page on a synchronous request until the settings had been
read (`settings.forceLoad`). Chrome delivers them over the very thread that
would be stalled, so that is impossible; upstream's fallback — answering every
protected API with `undefined` — breaks pages that merely use a canvas from an
inline `<head>` script.

Instead `lib/intercept.js` protects the page with the **built-in defaults** from
`document_start`, then reverts and intercepts again once the real settings
arrive a few milliseconds later. The APIs are never left unprotected; calls made
inside that window are faked according to the defaults rather than the user's
configuration. `settings.forceLoad()` and `extension.waitSync()` were removed
rather than left as silent no-ops.

Two spin-waits for the tab's cookie store id (`lib/randomSupplies.js`,
`lib/modifiedNavigatorAPI.js`) would have hung the tab for the same reason. They
are gone — Chrome has no contextual identities, so the value is always `""`.

### Background page → service worker

`background/background.js` `importScripts()` the modules in the order the
Firefox manifest listed them. Every runtime listener is registered
synchronously at the top level of `lib/main.js`, because a manifest V3 worker
only receives the event that woke it if the listener already existed in its
first event-loop turn; the handlers then wait for the settings themselves.

`browser.contentScripts.register()` (how Firefox baked the settings into a
`document_start` script) does not exist and is no longer needed — the bridge
reads them straight from `chrome.storage.local`.

The persistent-RNG clearing timer moved from `setTimeout` to `chrome.alarms`,
which survives the worker being shut down.

### Blocking webRequest → declarativeNetRequest

Manifest V3 has no blocking `webRequest`. The two features that used it were
rewritten on top of `declarativeNetRequest` (`lib/dnrRules.js`):

* **Data-URL protection** (`lib/dataUrls.js`) appends a
  `Content-Security-Policy` response header. Appending rather than setting
  keeps a policy the site sends itself intact.
* **User-Agent header** (`lib/navigatorHeaders.js`, split out of
  `lib/navigator.js`) sets the header from a rule that is rebuilt whenever the
  relevant settings change.

Independently of the CSP, the content scripts are registered with
`match_origin_as_fallback`, so `data:`, `blob:` and `about:` frames now get the
protection injected directly — something the Firefox version could not do.

### Toolbar UI

Manifest V3 merged `browserAction` and `pageAction` into a single `action`.
Chrome has no per-tab page action, so the notification list that Firefox showed
in the address bar is reached through a **Notifications** entry at the top of
the action menu, which navigates the popup to `pageAction/pageAction.html`.
Both popup documents share `themes/base/popup.css`, which pins the popup to
330px so it does not resize when switching between them.

`lib/browserShim.js` maps `browser.*` onto `chrome.*` for the service worker and
the extension pages (`browserAction` → `action`, plus `runtime.getBrowserInfo`).
`pageAction` is deliberately left undefined — the code base uses its absence to
detect "no per-tab action available".

### Icons and translations

Chrome does not render SVG for the toolbar or extension icon, so `build/icons.js`
rasterises them with headless Chrome into `icons/png/`.

Chrome also restricts i18n message names to `[A-Za-z0-9_]`, and 97 of
CanvasBlocker's contain `.`, `-` or `%` (mostly the `<setting>_options.<value>`
family) — the extension is rejected outright otherwise. `build/locales.js`
renames them, and `extension.getTranslation()` applies the identical
transformation, so ids assembled at runtime keep resolving and no call site
changed.


Behaviour differences
---------------------

* **Firefox containers** (`contextualIdentities`) do not exist in Chrome. The
  per-container navigator overrides and per-container RNG seeds are never
  selected, and the "clear persistent RNG for container" action is hidden.
* **User-Agent header rewriting** is coarser than on Firefox, because a
  declarativeNetRequest rule is static:
  * a `{random}` placeholder in the User-Agent template resolves once per rule
    build instead of once per request;
  * whitelist entries written as regular expressions cannot be expressed as a
    rule condition. They still apply to the JavaScript-level protection; only
    the HTTP header ignores them. `lib/dnrRules.js` logs which ones.
* **The first few milliseconds of a page** use the default settings rather than
  the user's — see above. Protection is active the whole time.
* **The blinking toolbar icon** is a still image. Chrome renders the raster PNG,
  so the SVG animation in `icons/browserAction-printedBlink.svg` is lost.
* **`privacy.websites.resistFingerprinting`**, which the options page reports on,
  is Firefox-only; the check is guarded and simply reports nothing.

### Pre-existing upstream issues, carried over unchanged

* `themes/default/presets.css` and `themes/default/sanitize.css` do not exist in
  the upstream package, so the options sub-pages log a 404 for the optional
  theme overlay. The pages have their own stylesheets and render correctly.
